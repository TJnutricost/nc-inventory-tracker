## The acceptance oracle for every race test (4B and 4C)
Concurrency tests verify the behavior SQLite produces when it **serializes** the same operations, never a stricter or looser rule someone assumed. For each orchestrated race of 2–4 operations on one asset, the same operations run through the SQLite modules on a fresh reference with the same fixture **in every serial order**; the PostgreSQL concurrent run's per-operation outcomes and final rows (masked: stamps, request_group UUIDs, module-written ids, queue_seq as a rank) must **equal one of those serial outcomes**. SQLite permits several overlaps (pending ordinary reservations, waiting entries, lapsed holds, checkouts that became overdue, "expected back" time, the 1:00 PM / 1:00 PM adjacency, a hold owner confirming over time recorded meanwhile); a test that conflicts with SQLite's actual behavior is reported with the evidence, never "fixed" in the module.

## 4B (opus/high): reservation writes + queue engine + effects
Every write path: take the asset id from a single unlocked lookup if needed (reservation/entry id → `asset_id`), then **`lockAsset` before any protected state decision or write, and re-read all relevant state under the lock**; one asset per transaction. Write functions join a caller's transaction (`isInTransaction(q) ? run(q) : withTransaction(run, q)`). `queue_seq` is computed per asset under the lock (no schema change). `create`/`approve`/`decline`/`cancel`/`shorten`/`insertReservation`/`note`; `evaluateAsset` (+ `insertPiece`, `close`); `insertEntry`/`announceJoined`. The protected helpers require the asset lock (`holdsAssetLock`, `ASSET_LOCK_REQUIRED`). Effects: plain-data effects registered through `onTransactionEnd(client, …)`, fired only when `committed` (at the outermost commit), dispatched via an injected notifier (`setNotifier`), resolving recipient/asset through the pool after commit; never throws; no mailer import. `evaluateAsset` registers a `holds_owed` trigger when it grants a hold.

Tests: lock-order guard (a `client.query` spy shows the asset `FOR UPDATE` precedes protected reads/writes of every write path; the initial id→asset lookup is allowed); reserve vs reserve; reserve vs `createAssignment`; overlapping approvals; approve vs cancel / cancel vs cancel / approve vs decline — **the loser gets the status message (400, e.g. "This reservation was cancelled." / "This reservation has already been decided."), exactly like SQLite's serialization; the 409 "just updated by someone else" is only reachable by a writer that skips the lock (tested with a deliberate non-locking writer)**; cancel/shorten promoting seeded waiters in FIFO order with correct re-split; rollback leaves no rows/activity/effects; no email on a failed transaction; slow notifier does not delay a second transaction on the same asset; pool returns to baseline. Operations that need 4C code (join, confirmHold, sweep) are tested in 4C, not forced into 4B.

## 4C: waitlist actions + sweep + hold email
Waitlist actions (write functions join an outer transaction; same lock-first rules; `updateDates` adds the `updated` flag to `waitlist_joined`) + `processDue` (own committed transaction, requested asset only on request paths; global `sweep` = one transaction per asset, ascending id) + global claim-based `dispatchHoldEmails` (`hold_email_at` atomic claim, at-most-once) wired to the `holds_owed` effect, incl. the existing run-even-when-the-mutator-throws (`settling`) behavior.

Tests: join/`queue_seq` contention, `confirmHold` vs expiry, double confirm, cancel vs join, sweep vs request, sweep continues past one failing asset, at-most-once hold email (claim, no duplicate), failure to send never reverses state, no SMTP under lock; the same serial-order oracle. Reports any behavior difference rather than adjusting code to satisfy tests.

## Notes that 4C must keep
- SQLite returns `queue_seq` ties (split pieces) in `idx_waitlist_queue` order: status text ('held' before 'waiting'), then rowid. The 4A read queries order `queue_seq, status, id` to match. `evaluateAsset` orders `queue_seq, id` literally (as SQLite does explicitly); keep that order there.
- `findBlockers`, `plan`, `hasOwnOverlap`, `hasOwnHold` and `classify` take `q`: inside a write, pass the transaction client after `lockAsset`.
- Hold expiries are written with `NOW_PLUS('$n')` from `src/pg/time.js` (SQLite `datetime('now', '+N seconds')`); the "available until" activity text reads its own `time.nowPlus()`.
- `queue_seq` is per asset (`MAX + 1` over the asset's entries, under the lock); `updateDates` (back of the line) must use the same per-asset rule.
- Test support: `test-support/pg-write-support.js` (masks, state dumps, fixture recorder, `serialOracle`, `race`, query spy, SQLite-writer mail environment) and `pg-twin.syncSequences()` (aligns the next ids of both engines).
