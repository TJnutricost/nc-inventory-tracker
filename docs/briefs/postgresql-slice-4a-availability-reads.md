## Design rules
1. **Same names, same return shapes, same error `status`/messages.** Each function becomes `async` and takes an executor `q` (a `pg` Pool *or* a transaction client; anything with `.query`) instead of `db`. The Slice 5 conversion must be mechanical: add `await`, swap the first argument.
2. **Import pure helpers; don't copy them.** Allowed `require`s of SQLite-side modules, which must be safe at load time: `src/timeRange.js` (`T.*`), `src/assignments.js` (`capacity`), and the pure exports of `src/availability.js` (`monthWindow`, `periodsFor`, `dayState`, `reserveEligibility`, `checkoutEvents`) and `src/reservations.js` (`LIVE`, `MAX_DATE`, `httpError`, `validDate`, `validateRange`, `rangeOf`, `whyBlocked`, `phaseOf`, `fmt`, `span`, `when`). Private pure helpers that are not exported (`summaryDays`, `allCheckouts`/`eventOn`, the `assetRow` shaping, `present`'s shaping; `responseMinutes` is exported and importable) are repeated in `src/pg/` and covered by the differential tests; list them in the report.
3. **SQLite must never load.** `src/reservations.js` and `src/waitlist.js` lazily `require('./mailer')`, which requires `./db`, which opens SQLite and creates `data/`. So: never call an SQLite-side function that touches `db`/`mailer`/`waitlist()` (e.g. `reservations.create`, `waitlist.sweep`). Add a test (`test/pg/pg-no-sqlite.test.js`) that loads every `src/pg/*` module in a fresh child process (or a clean `require.cache`) and asserts `src/db.js`, `src/mailer.js` and `better-sqlite3` are NOT in `require.cache`, and that no `data/` directory was created. (Slice 3 only grepped.)
4. **Catalog.** `availability` uses `src/pg/catalog` (async; `loadIndex`, `isLive`, `subtreeIds`, `getNode`, `pathText`). Do not touch the SQLite catalog cache. Load the index once per call, then resolve paths/liveness synchronously from it so `assetRow` stays cheap. If any needed helper is missing from `src/pg/catalog` report it; do not edit the SQLite catalog.
5. **Time.** "Today" = `src/pg/time.js` `today(q)` (UTC date, D-26: keep, do not "fix"). `hold_expires_at > NOW` comparisons use `NOW` from `src/pg/time.js` as text, like SQLite. The JS clock (`T.nowKey`, `APP_TIMEZONE`) is used exactly where the SQLite code uses it. Add the "now + N seconds" helper to `time.js` with the same truncated-UTC text format and tests (format by regex, fractional truncation, `hold_expires_at > NOW` ordering).
6. **NULL ordering and sort (SQLite NULLs sort first ASC / last DESC; PostgreSQL is the opposite).** Make every ordering explicit and identical to SQLite:
   - `ORDER BY start_date, start_time NULLS FIRST, id` (findBlockers reservations and holds);
   - `ORDER BY w.closed_at DESC NULLS LAST, w.id DESC` (waitlist closed list);
   - `ORDER BY w.asset_id, w.queue_seq, w.id` (split pieces share `queue_seq`; add the `id` tie-breaker, also on the availability waitlist query `ORDER BY w.queue_seq, w.id` and on `ORDER BY s.checked_out_at, s.id`);
   - `ORDER BY a.name COLLATE NOCASE, a.tag` → `ORDER BY lower(a.name), a.tag` (exact under the baseline `"C"` collation: ASCII-only folding, byte order for the rest; add a non-ASCII-name ordering test and keep the Slice 3 lookup idiom). This is the Slice 3 carry-over for `availability.js` L145.
   - There is no `LIKE`/search in these three modules (search lives in `server.js`, Slice 5); if you find any, convert with `ILIKE`/`lower()` both sides and report.
7. **SQL idioms.** `?` → `$n`; `end_time IS ?` is a write (4B) but note `IS NOT DISTINCT FROM`; the SQLite `lapsed` column (`(status='held' AND hold_expires_at <= datetime('now')) AS lapsed`) is 0/1 in SQLite and boolean in PostgreSQL: normalize so every consumer and returned JSON is identical (never leak `true`/`false` where SQLite returned `1`/`0`). `COUNT(*)` is already a JS number (the pool parses int8). Dynamic `IN (…)` lists: use `= ANY($1::int[])`. Non-numeric/out-of-range ids map to "not found"/the same 400 as SQLite, not a PG `22P02` (as in Slice 3).
8. **Consistency of reads.** These are multi-statement reads on a pool in READ COMMITTED and are not a snapshot (SQLite was effectively one). That is acceptable: they are advisory and every write (4B/4C) re-checks under the asset lock. Do not open transactions in 4A (a read called from inside a caller's transaction must keep working with that client). Document this in the module headers and the report.
9. **Concurrency note for later slices (document in headers, do not build):** all write paths in 4B/4C lock the asset first (`lockAsset`, Slice 2 rule) and re-read dependent rows under the lock; `findBlockers`/`classify` take `q` so they run on the transaction client there.

## Tests (`test/pg/`, run under `npm run test:pg`, skipped by plain `npm test`)
Port the *scenarios* of `test/availability.test.js`, `test/reservations.test.js`, `test/reservation-times.test.js`, `test/partial-fulfillment.test.js` and `test/waitlist.test.js` that exercise read paths, using the module API instead of HTTP, plus **differential tests**: build the same scenario in an in-memory SQLite DB (reuse Slice 3's `buildSqliteReference`) and in PostgreSQL, run both modules, and require **identical output** (deep-equal) and identical errors.
- **Availability:** every day state (`available`, `occupied`, `expected`, `reserved`, `partial`, `repair`, `ineligible`, `archived`, `past`); scopes asset / node (subtree) / global for admin and employee; employee anonymity and narrowing (no holder fields, hidden assets, not-lendable); seats; permanent assignments excluded from broad calendars; truncation flags; month validation 400s; `todayStates` incl. `expected_back`; holds count as reserved only while `hold_expires_at > NOW` (an expired-but-unswept hold counts for nothing).
- **Blockers/plan/classify:** each blocker kind (`reservation`, `hold`, `pending_hold`, `checkout` bounded by due date AND due time; permanent/overdue unbounded); half-open adjacency (1 PM return / 1 PM pickup passes); `T.splitFree` free/busy pieces; every `classify` outcome (`reserve`, `partial`, `waitlist`, `invalid`, `unavailable`, `own_reservation`, `own_hold`, `own_waitlist`) with messages and statuses; `reservers` list; `excludeEntryId`; `rangeCheck` shape.
- **Waitlist reads:** `list` (employee vs admin, `open`/`closed`/invalid status 400, orders, LIMIT), `get` (404/403), `present` (phases incl. lapsed hold → `expired`, fulfilled → `checked_out`/`pending`/`confirmed`/`reservation_declined`/`reservation_cancelled`; `position` among overlapping entries; button flags; admin-only fields), `counts` (admin and employee).
- **Mutation checks (report them):** removing `NULLS FIRST` and replacing `lower(a.name)` with plain `a.name` must each make a differential test fail.
- **Time:** the new now-plus-seconds helper (format, truncation, comparison).
- **No-SQLite test** (Design rule 3).
- **Deterministic by construction.** No `sleep`, no dependence on wall-clock tier/midnight boundaries: seed `hold_expires_at`/dates by direct INSERT/UPDATE relative to the database clock with generous margins, and for anything using the JS clock (`T.nowKey`, `APP_TIMEZONE`) keep rows far from tier (4 h / 24 h) and midnight boundaries. Do not copy the pattern of the 3 flaky tests. Run the new suites at least 10 times in a row and report.
