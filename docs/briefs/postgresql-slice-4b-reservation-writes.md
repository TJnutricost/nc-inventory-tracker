## Approved architecture decisions (owner, 2026-10-14)
1. **Structural hold-email trigger.** `evaluateAsset` registers a `holds_owed` effect (through the effects mechanism, i.e. `onTransactionEnd`) whenever it grants at least one hold; it fires only after a successful COMMIT (dropped on rollback). It is only a **trigger**. The existing **global, claim-based** `dispatchHoldEmails` (the `hold_email_at` atomic claim, the sweep, the run-even-when-the-mutator-throws `settling` wrapper) is 4C and stays exactly as is: at-most-once, never duplicated, never retried into a duplicate. Therefore a spurious or repeated `holds_owed` is harmless (nothing owed = nothing sent), and a dropped one only delays an email until the next sweep, never loses it. Do not add missed-notification or duplicate-notification paths.
2. **Lock-held guard.** `holdsAssetLock(client, assetId)` in `src/pg/transaction.js`. Protected helpers require the right asset lock before any protected state read or write. The one allowed exception: a single initial id→`asset_id` lookup (reservation id, entry id) used only to learn which asset to lock, followed by `lockAsset` and a **re-read of all current state under the lock**.
3. **Join an outer transaction (the `createAssignment` pattern).** Each write function: `isInTransaction(q) ? run(q) : withTransaction(run, q)`. A pool passed from inside a transaction is still rejected as nesting (test it). When joined, effects wait for the OUTERMOST successful commit (there is only one transaction; `withTransaction` refuses real nesting). The caller (Slice 5) must not have read or written this asset's dependent rows before calling; the function takes the asset lock itself first (re-locking a row the same transaction already holds is a no-op).

## Design rules
1. **Same names, same return shapes, same error `status`/messages, same order of checks as the SQLite functions.** Each function is `async` and takes executor `q` (pool or transaction client) instead of `db`. Read `src/reservations.js` and `src/waitlist.js` line by line; port statement for statement (same activity `action` strings and `details` text, same order of writes). `create` returns `{ request_group, requested, reserved, waitlisted }`; `approve`/`decline`/`cancel`/`shorten` return the reloaded reservation row; `evaluateAsset` returns the granted ids. Input validation that SQLite does before opening its transaction (e.g. `shorten`'s `T.cleanTime(newEndTime, 'return time')`) stays before the transaction, so error precedence is unchanged.
2. **Lock first, re-read under the lock (Slice 2 ordering rule).**
   - `create(q, {assetId, …})`: the first statement after BEGIN is `lockAsset(c, assetId)` (invalid/unknown asset → the same 404 `Asset not found` SQLite's classify path gives); then `classify(c, …)` (4A), then the inserts. Use the locked row as `asset`.
   - `approve`/`decline`/`cancel`/`shorten`: ONE unlocked `SELECT asset_id FROM reservations WHERE id = $1` (none → 404 `Reservation not found`), then `lockAsset`, then `load` again under the lock and run every check against that fresh row, then the writes. `decline`/`cancel`/`shorten` then call `evaluateAsset` on the same client.
   - One asset per transaction; never lock a second asset.
   - Pass the TRANSACTION CLIENT to `findBlockers`/`plan`/`classify`/`hasOwnOverlap`/`hasOwnHold` (4A) so they re-read under the lock.
3. **Guard the protected helpers.** `insertReservation`, `evaluateAsset`, `insertEntry`, `insertPiece` and `close` call an `assertAssetLock(client, assetId)` that throws a plain `Error` (code `ASSET_LOCK_REQUIRED`, never an HTTP-status error) if `client` is not in a transaction or does not hold that asset's lock. This is a programming-error net for Slice 5 (check-in calls `evaluateAsset`), not a user-facing message.
4. **`holdsAssetLock` semantics (transaction.js, additive, no behavior change for existing callers).** Tracked per client as a set of locked asset ids, recorded only AFTER the `FOR UPDATE` query succeeds; false outside a transaction; false for any other asset. **Cleared when the transaction ends** (COMMIT, ROLLBACK, failed ROLLBACK/destroy, any throw) before the client is released, and also reset at BEGIN, so a pooled client reused by the next transaction can never carry a lock record across. Tests must prove this with a pool of max 1 (same client reused): lock asset 1 in tx A and commit → tx B on the same client has `holdsAssetLock(client, 1) === false`; same after rollback and after an error thrown inside the callback; lock of asset 1 does not imply asset 2; calling `evaluateAsset` with a pool, with a transaction client that has not locked, and with a client that locked a different asset all throw `ASSET_LOCK_REQUIRED`. Existing `test/pg/pool-transaction.test.js` stays green.
5. **Effects (`src/pg/effects.js`).**
   - An effect is plain data: `{ type, … }`. Types in 4B: `request_recorded` `{ employeeId, assetId, requested, reserved, waitlisted }` (always, after a successful `create`); `waitlist_joined` `{ waiterEmployeeId, assetId, entry, reserver }`, one per DISTINCT blocking reserver employee, only when `create` waitlisted pieces (the entry chosen as SQLite's `announceJoined` does: `entries.find(overlaps reserver) || entries[0]`; `updated` flag reserved for 4C); `holds_owed` `{ assetId }` (see decision 1; at most one per asset per transaction).
   - `registerEffect(client, effect)` must be called inside `withTransaction` on that transaction's client (else throws a programming error) and only AFTER the writes it describes have succeeded. Internally it registers ONE stable flush callback per client via `onTransactionEnd`; the flush runs only when `{ committed: true }` and discards everything on rollback. Effects of one transaction are dispatched in registration order, sequentially; different transactions dispatch independently.
   - Dispatch goes to an injected notifier (`setNotifier(fn)`; default **no-op**, `setNotifier(null)` resets). The notifier receives the plain effect and resolves recipients/asset itself (through its own pool: effects carry ids, never a pool; use the 4A `emailOf`/`loadAsset` helpers there). Dispatch is asynchronous and **never awaited by the transaction or the caller**: it runs after COMMIT, so the asset lock is already released, and it must never throw or reject out of the module (catch, `console.error('[effects]', …)`). Track in-flight dispatches so `whenIdle()` resolves when none remain (tests need it).
   - **No email before commit; no SMTP/slow work while an asset lock is held; an effect/notifier failure never reverses committed state.** `src/pg/effects.js` imports no mailer and nothing from SQLite.
6. **`queue_seq` is per asset, under the lock:** `(SELECT COALESCE(MAX(queue_seq), 0) + 1 FROM waitlist_entries WHERE asset_id = $n)` in `insertEntry` (SQLite used a table-wide MAX; ordering only ever matters within an asset, split pieces keep sharing the entry's `queue_seq`). No schema change.
7. **FIFO ordering is literal.** `evaluateAsset` reads the waiting entries `ORDER BY queue_seq, id` (NOT the 4A list order `queue_seq, status, id`; that was only to mirror SQLite's index order in list screens). Give every other loop in `evaluateAsset` an explicit `ORDER BY id` (SQLite returned rowid order). Preserve: an older still-blocked entry does not hold up a younger eligible one; each hold makes its time unavailable for the entries behind it (so `freeParts`/`plan` re-reads blockers per entry, on the client, after the previous grant); the entry itself becomes the first free piece, every other free piece is a new held row and every busy piece a new waiting row, all sharing `queue_seq`/`queued_at`/`request_group`/`created_at`.
8. **SQL translations.** `?`→`$n`; `lastInsertRowid`→`RETURNING *` (return the inserted row); `.changes`→`rowCount`; `datetime('now')`→`NOW`; `datetime('now', ?)`→`NOW_PLUS('$n')` (seconds); the "available until" activity text is computed with a separate `time.nowPlus(c, secs)` exactly as SQLite does with a separate query (do not derive it from the stored row); `end_time IS ?`→`end_time IS NOT DISTINCT FROM $n`; `date('now')`→`time.today(c)`. Keep the two clocks as they are (DB clock text for stored stamps and `hold_expires_at > NOW`, JS `T.nowKey()`/`APP_TIMEZONE` for tiers and `T.endKey` comparisons, `new Date().getUTCSeconds()` in `offerSeconds`); D-26 "today is UTC" stays. Import `responseMinutes`, `offerSeconds`, `RESPONSE_MINUTES` from `src/waitlist.js` (pure; they are exported).
9. **CAS guards stay** (`… WHERE status = 'pending'` etc., `rowCount === 0` → the same 409 "just updated by someone else"). Under the asset lock and a fresh re-read they are unreachable by locked writers, so a concurrent approve/cancel loser sees the **status message** (400 "This reservation was cancelled." / "This reservation has already been decided."), exactly like SQLite's `BEGIN IMMEDIATE` serialization; the 409 is defense in depth against a writer that skips the lock (Slice 5 bug). Keep it and test it with a deliberate non-locking writer.
10. **Never load SQLite.** Do not call SQLite-side functions that reach `db`/`mailer` (`reservations.create`, `waitlist.*` writers). Extend `test/pg/pg-no-sqlite.test.js` to cover `src/pg/effects.js` and the new code (child process, `require.cache` has no `src/db.js`/`src/mailer.js`/`better-sqlite3`, no `data/` created).
11. **Accepted, document in headers/report:** (a) a concurrent employee deactivation is not locked (outcome is simply "before" or "after"); (b) `lock_timeout` and pool sizing are Slice 5 (a transaction waiting for an asset lock holds one of the 10 pool connections; keep concurrency tests within the pool); (c) nothing here sends mail.

## PRODUCT SAFEGUARD: preserve SQLite behavior exactly (read before writing any test)
Concurrency tests must verify the **same behavior SQLite produces when it serializes the same operations**, never a stricter or looser rule that someone assumed. SQLite permits several overlaps that a naive "no overlaps ever" invariant would wrongly forbid. **Permitted today (do not prohibit, do not "fix"):** pending ordinary reservations (they hold no time and may overlap anything, including each other; approving the second is what is refused); waitlist entries that are merely waiting (demand, never block); lapsed/expired holds and every closed/past row; a checkout that became overdue after a reservation was made; a reservation starting after a bounded checkout's due date+time ("expected back" is not an overlap); the 1:00 PM / 1:00 PM adjacency; a waitlist-born pending reservation counts as a blocker but an ordinary pending one does not; a hold owner confirming over time that something else recorded (4C).
1. **Serial-order oracle for every race test (required).** For each orchestrated race of 2 or 3 operations on one asset, run the operations through the SQLite modules on the in-memory reference (`buildSqliteReference`/`pg-twin`) in **every serial order** (2! or 3!), recording each operation's outcome (success + result summary, or error status+message) and the final rows (masked, see Tests). The PG concurrent run's outcomes and final rows must **equal one of those serial outcomes**. PG may not refuse anything that every serial SQLite order would allow, nor allow anything no serial order allows. This is the acceptance oracle, not a hand-written invariant.
2. **Invariant checks (optional, narrow).** If you add a randomized invariant test, it may only assert rules the tested paths guarantee from clean, non-overlapping fixtures (e.g. in 4B-only histories no two CONFIRMED reservations of one asset overlap by `T.overlaps`, since `create` and `approve` both refuse that), and it must exclude every "permitted" case above.
3. **If any test in this brief conflicts with SQLite's actual behavior, flag it in the report with the SQLite evidence (the failing scenario and both outputs); do not change module behavior to satisfy it, and do not silently weaken the test.**

## Test infrastructure notes (known hazards)
- **Identity sequences.** `pg-twin` inserts fixtures into PG with explicit ids, which does not advance PG's identity sequences; module-inserted rows would then collide with fixture ids. After fixtures are loaded, advance every touched table's sequence (`setval(pg_get_serial_sequence('<table>','id'), (SELECT COALESCE(MAX(id),1) FROM <table>))`), as a helper used by the twin.
- **Differential harness loads SQLite writers.** The SQLite `create`/etc. lazily require `./mailer` → `./db`. Set a temp `DATA_DIR` and `NC_NO_EXTERNAL_MAIL=1` BEFORE requiring them (precedent: the Slice 3 settings parity test, `test/helpers.js`). These differential files are separate from `pg-no-sqlite`. No test may send real email.
- **Masking.** Compare PG vs SQLite outputs after masking values the two clocks/generators legitimately differ in: `created_at`/`updated_at`/`decided_at`/`cancelled_at`/`closed_at`/`queued_at`/`hold_started_at`/`hold_expires_at` (assert format by regex and, for holds, that `expires − started` equals the expected tier seconds ±1), `request_group` UUIDs (assert shared-ness: pieces of one request share one group, different requests differ), and identity ids that depend on insertion order (compare relative structure). `activity` rows compare `action` + `details` + subject/asset/actor, with stamps inside `details` ("available until …") masked by format.
- **Query spy** (`test-support/pg-query-spy.js` or similar): wraps a transaction client's `query`, recording SQL text in order, for the lock-order guard.

## Tests (`test/pg/`, run under `npm run test:pg`, skipped by plain `npm test`)
Port the write-path scenarios of `test/reservations.test.js`, `test/reservation-times.test.js`, `test/partial-fulfillment.test.js` and `test/waitlist.test.js` (only the parts exercising `create`/`approve`/`decline`/`cancel`/`shorten`/`evaluateAsset`) to the module API, plus differential tests against the SQLite modules.
- **Functional/differential:** `create` all-free → reserved (confirmed, or pending when the asset requires approval); all-unavailable → 409 "Join the waitlist for that time instead."; partial → reserved + waitlisted sharing one `request_group`; timed and date-only ranges, half-open adjacency (8–1 reserved then 1–5 request = reservation only; 12–2 vs 8–1 → 12–1 waitlisted, 1–2 reserved); every refusal (ineligible asset/person, past/invalid dates, own overlap, own hold, own waitlist) with identical status+message; `approve` (every error branch, re-check of the whole range, ineligible asset, inactive person, start passed, blocked → 409 "Can't approve: …" and stays pending); `decline` (and a declined waitlist-born pending reservation giving its dates back to the queue); `cancel` (own/other 403, admin on confirmed OK, admin on pending → 400 "Decline it instead", already closed, already over, activity text incl. "· cancelled by IT"); `shorten` (earlier date, earlier time, same, later, before pickup, past, pending, closed, other person's) incl. the `IS NOT DISTINCT FROM` guard with NULL and non-NULL `end_time`; `evaluateAsset` on seeded waiting entries: whole-range offer, partial offer + remaining waiting piece, multiple free pieces, an older blocked entry not blocking a younger eligible one, overlapping entries served FIFO by the holds they create, entries closed as expired (lapsed hold / dates passed / interval ended) with the same activity rows, the three response tiers (24 h / 2 h / 30 min) and an offer capped at the end of the interval, `waitlist_split` / `waitlist_hold_started` activity text, ties on `queue_seq` ordered by `id`.
- **Lock-order guard:** for each write path the query spy proves the first statement after BEGIN is either the single id→`asset_id` lookup or `SELECT * FROM assets WHERE id = $1 FOR UPDATE`, and that the `FOR UPDATE` precedes every other read or write of protected state. Plus the `holdsAssetLock` tests (design rule 4) and the `ASSET_LOCK_REQUIRED` tests.
- **Concurrency (oracle-checked; orchestrate races deterministically, e.g. hold the asset lock on a third connection until all contenders are waiting, as Slice 3 did):**
  (a) N≥4 simultaneous `create` of overlapping ranges on one asset, approval OFF: outcomes equal a serial order (first confirmed, later overlapping ones refused or split per SQLite) and final rows have no overlapping confirmed reservations; with approval ON all are pending, exactly as SQLite;
  (b) `create` vs `pg/assignments.createAssignment` on the same asset and overlapping time (both orders in the oracle);
  (c) two `approve` calls on overlapping pending reservations: one approved, the other 409 "Can't approve: …" and still pending;
  (d) `approve` vs `cancel` of the same reservation, `cancel` vs `cancel`, `approve` vs `decline`: the loser gets the status message (400), not the 409;
  (e) `cancel`/`shorten` that free time while waiting entries exist: promotions are FIFO and re-split correctly, holds appear exactly once, and two concurrent releases on the same asset never double-offer the same time;
  (f) operations on two different assets proceed independently (a held lock on asset A does not block asset B);
  (g) no deadlock; pool `waitingCount`/`idleCount` back to baseline after each suite; keep contenders within the pool (≤ 9 plus a sampler on its own pool).
- **Rollback:** a failure injected at the LAST statement (trigger on the final activity insert) in `create`, `cancel` and `shorten` leaves no reservation, no waitlist row/piece, no hold, no activity, no status change, and **no effects**; also an FK failure (e.g. nonexistent `actorAccountId`).
- **Effects:** a failed transaction fires nothing; success fires each effect exactly once, after COMMIT, in order; a throwing notifier and a rejecting async notifier leave committed state untouched and do not surface; effects registered inside an OUTER transaction that also calls these functions fire once at the outer commit and not at all if the outer rolls back; `holds_owed` fires only when a hold was granted and at most once per asset per transaction; the set of effects equals the emails SQLite sends for the same `create` scenarios (compare with the SQLite mailer's logged outbox recipients/subjects: same number of messages to the same people); effects module has no mailer/SQLite import. **Slow notifier, deterministically:** the fake notifier blocks on a test-controlled deferred promise (no timers or sleeps); while it is blocked, a second transaction on the same asset must complete (proving the lock is not held during dispatch); then release the gate and `await whenIdle()`.
- **Deterministic by construction:** no `sleep`, no reliance on wall-clock boundaries; build times relative to the DB/JS clock with large margins; set `APP_TIMEZONE=UTC` in these suites so the two clocks agree; prefer starts ≥ 1 day ahead (24 h tier) and, for the 2 h and 30 min tiers, margins ≥ 1 h from each tier boundary; if the run happens in a window where those margins cannot be met (within 15 min of UTC midnight), skip that single test with an explicit message instead of failing. Never copy the pattern of the 3 flaky tests. Run the new/changed suites **at least 10 times in a row** and report.
- **Mutation checks (report each):** dropping the lock call in `create`; moving `lockAsset` after the `classify`; `queue_seq, id` → `id` in `evaluateAsset`; registering effects before the writes; firing effects on rollback; not clearing the lock record at transaction end — each must make a test fail.
