## What 5A builds
1. **Shared mail core + two data adapters (owner decision 7; preserves D-35 to D-39).**
   - New `src/mailCore.js`: no `src/db.js`, no SQLite, no `src/pg` import. It holds everything pure/transport: `APP_URL`, sender address, envelope (From = display name + verified sender; Reply-To = IT contact; `MAIL_ALLOW_IT_FROM`), `NC_NO_EXTERNAL_MAIL` (no transport is ever built from the environment), the SMTP transport, `esc`/`layout`/`assetLine`, `deliveryFor` + `MAIL_TEST_RECIPIENT` redirect (invalid value fails closed: nothing sent, outbox 'failed'), range/date formatting, every notify template as a function returning `{ to, subject, html }`, and delivery that writes one outbox row per recipient (`logged` / `sent` / `failed`, `delivered_to`) through an adapter.
   - Factory `createMailer(adapter)`; adapter = `{ record(row), adminEmails(), getSettings() }` (sync or async). The mailer instance owns its transport (`setTransportForTests`, `mailConfigured`, `mailEnvelope`, `testRecipient`, `deliveryFor`).
   - `src/mailer.js` becomes the thin SQLite adapter over the core with **exactly the same exported API and behavior** (`notify.*` fire-and-forget returning undefined, `APP_URL`, `setTransportForTests`, ...). **Before refactoring, capture a golden master** of the current mailer (every `notify.*` with fixed fixtures: recipient list, subject, html, outbox rows, envelope, test-recipient redirect, failed transport) into a test fixture; after the refactor the output must be byte-identical. All existing mail tests (e.g. `test/seed-mail-safety.test.js`) pass unchanged.
   - `src/pg/mailer.js`: the PostgreSQL adapter (outbox insert into the PG `outbox` table, `adminEmails` from PG `accounts`, settings from `src/pg/settings.js`) and `createPgMailer(pool)`. Its notify methods return a promise that never rejects (errors logged); they never send before the caller has committed (they are only called from effects).
   - `src/pg/notifier.js`: `createNotifier(pool, mailer)` returns `fn(effect)` for `setNotifier`: `request_recorded` -> `requestRecorded`, `waitlist_joined` (incl. `updated`) -> `waitlistJoined`, `hold_email { entry }` -> `waitlistHold`, `holds_owed { assetId }` -> `waitlist.dispatchHoldEmails(pool)`; unknown type -> logged, ignored. Recipients and asset resolved through the pool after commit with the 4A `emailOf` / `loadAsset` (no email address -> skipped, as SQLite's `send` does). `installNotifier(pool, mailer)` calls `setNotifier` and returns an uninstall function. **Nothing calls it yet (5D wires it).** **No loop and no duplicate:** `hold_email` never triggers `holds_owed`; `holds_owed` only calls the claim-based `dispatchHoldEmails`, whose `hold_email` effects go to the mailer (test: a hold produces exactly one email, `hold_email_at` set once, with the notifier installed and with a throwing mailer).
2. **Single-flight sweep scheduler `src/pg/sweep.js` (decision 5).** `createSweepScheduler({ pool, intervalMs = 60_000, run = waitlist.sweep, log })` -> `{ tick(), start(), stop() }`. `tick()` never throws and returns `{ ran: true, result }` or `{ ran: false, reason: 'in_flight' | 'locked' }`. In-process flag (a tick while one is running is skipped) PLUS a session-level PostgreSQL advisory lock (`pg_try_advisory_lock`) taken on a dedicated client (`pool.connect()`) held for the whole sweep and released in `finally` (if the unlock fails, destroy the client; a dead connection frees the lock). New key constant next to `src/pg/migrate.js` `ADVISORY_LOCK_KEY` (4_651_201_400_017), documented, distinct. `start()` uses an `unref()`'d `setInterval`; `stop()` clears it and awaits an in-flight sweep. Not wired to `server.js`.
3. **Lock timeout, pool, 503 (decision 6; initial values, subject to testing).**
   - `lockAsset` (src/pg/transaction.js) sets a **transaction-local** timeout right before its `FOR UPDATE` (`SELECT set_config('lock_timeout', $1, true)`), default **5000 ms**, overridable for tests (`setLockTimeout(ms)`, env `NC_LOCK_TIMEOUT_MS`). It must not leak to other statements or to the next transaction on the same pooled client (test with a pool of max 1: `SHOW lock_timeout` is the default afterwards, after commit, rollback and error).
   - PostgreSQL error `55P03` from the asset lock -> an error with `status: 503`, `code: 'ASSET_BUSY'`, message exactly **"This item is busy right now. Please try again in a moment."**; the transaction rolls back (no rows, no activity, no effects). Applies to every write path through `lockAsset` (including `lockOr404`), the request-path due step and the main transaction alike. In the sweep, a timed-out asset is reported in `failed` and the sweep continues.
   - Pool size stays **10**. A pool CHECKOUT timeout inside `withTransaction` (`connectionTimeoutMillis`, 5 s) -> `status: 503`, `code: 'DB_BUSY'`, message "The system is busy right now. Please try again in a moment." (planner default, distinct from the item message; other connection errors are NOT remapped). Migrations/advisory locks are not subject to the asset timeout.
   - Existing 4B/4C race tests must still pass with the 5 s default (they release locks within ms); if one needs longer, raise the timeout inside that test only.
4. **4C refinements (decisions 3 and 4).**
   - `confirmHold` joined to an outer transaction is **rejected**: when `isInTransaction(q)` it throws a plain `Error` with `code: 'CONFIRM_HOLD_NEEDS_POOL'` before any read or write (programming error, never an HTTP status). Update the 4C tests that exercised the joined confirm. `join`, `updateDates`, `declineHold`, `leave` keep joining as before.
   - **Expired-hold gap, refined:** make `recordLapses` return how many rows it closed. In the non-joined request path, if the main transaction recorded >= 1 lapse and then fails with an HTTP-status error (4xx, not the 503s above), then after the ROLLBACK re-run the standalone due step for that asset (its own committed transaction, same email gating as the first due step), then rethrow the ORIGINAL error. Result: the refused request's own writes are all rolled back (no partial changes), while the lapse record and the queue movement SQLite would have made are committed, and the next person is offered and emailed exactly once. A failure in the re-run is logged and never replaces the original error. Non-HTTP errors and 503s do not trigger it.

## Tests (`test/pg/` for PG; the golden master and SQLite mailer tests run under plain `npm test`)
- **Mailer:** golden-master identity for the SQLite mailer; PG mailer == SQLite mailer for every template (to, subject, html, outbox rows) incl. test-recipient redirect, invalid `MAIL_TEST_RECIPIENT` fail-closed, `NC_NO_EXTERNAL_MAIL`, From/Reply-To/`MAIL_ALLOW_IT_FROM`, `logged`/`sent`/`failed` outbox rows, a throwing transport; PG outbox rows land in the PG table. `pg-no-sqlite` extended to `mailCore.js`, `pg/mailer.js`, `pg/notifier.js`, `pg/sweep.js` (fresh child process: no `src/db.js`, no `better-sqlite3`, no data dir).
- **Notifier:** each effect type renders the same email as the SQLite flow for the same scenario (reuse the 4C parity fixtures, now through the PG mailer); email failure leaves committed rows untouched; no email on rollback; no SMTP while an asset lock is held (gated slow transport; a second transaction on the same asset and `FOR UPDATE NOWAIT` succeed); at-most-once hold email under N concurrent dispatchers with the notifier installed; no `holds_owed`/`hold_email` loop; uninstall restores the no-notifier behavior (nothing claimed).
- **Sweep scheduler (no real 60 s waits; call `tick()`):** in-process single flight (second tick skipped while the first is gated); two schedulers on two pools (two instances) racing: exactly one runs, the other gets `locked`; the lock is released after success, after a throwing `run`, and when the holding connection is killed; `stop()` awaits an in-flight sweep; a sweep failure never throws out of `tick()`; the dedicated connection is returned (pool baseline).
- **Lock timeout:** lock held on a third connection, contender with a small test timeout -> 503 `ASSET_BUSY` with the exact message after about the timeout, nothing written, no effects; no leak of `lock_timeout` to later statements (pool max 1); uncontended locks unaffected; a held lock on asset A does not time out a write on B; 12 contenders on one locked asset with pool 10 -> every one ends in success or a 503 (`ASSET_BUSY`/`DB_BUSY`), none hangs, pool and waiter counts back to baseline, no deadlock; sweep with one timed-out asset reports it in `failed` and continues.
- **4C refinements:** joined `confirmHold` throws `CONFIRM_HOLD_NEEDS_POOL` and wrote/read nothing; pool path still behaves exactly as in 4C. Gap test (existing seam) for confirm, decline and leave refused after a lapse recorded in the main transaction: the refused request's own writes are absent, the lapse is recorded (entry `expired`), the queue moved, the next person offered and emailed exactly once, the original error status/message returned, and the final masked state equals SQLite's serial order [processDue, refused op]; a successful request in the gap is unchanged; a 503 or non-HTTP failure does not trigger the re-run.
- **Mutation checks (each must fail a test; report):** drop the advisory lock; drop the in-process flag; lock_timeout set session-wide instead of local; remove the 55P03 mapping; remove the re-run after a gap refusal; allow joined `confirmHold`; mail core reading `process.env` NC_NO_EXTERNAL_MAIL wrongly (send when blocked); `holds_owed` mapped to a direct send.
- Deterministic by construction (no sleeps beyond the injected small timeouts, no wall-clock boundaries; time-tier tests keep the 15-minute-from-UTC-midnight skip rule). New and changed suites plus the 4A/4B/4C suites and `pool-transaction`: **10 consecutive runs**, 0 skips, report.
