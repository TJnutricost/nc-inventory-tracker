## Priorities (owner, in order; every rule below serves these)
1. Waitlist positions and FIFO preserved (`queue_seq` per asset, assigned under the asset lock; `updateDates` = back of the line; `evaluateAsset` order `queue_seq, id` literal).
2. Partial-day reservations preserved (times, half-open adjacency, split pieces keep place in line).
3. Hold confirmation and expiration rules preserved (tiers 24 h / 2 h / 30 min, cap at interval end, hold = holder's priority, lapsed hold counts for nothing at the instant it expires).
4. No conflicting allocations (every write: `lockAsset` first, re-read under the lock, one asset per transaction).
5. Request-path expiry is asset-scoped; the 60-second global sweep stays (D-47 point 2).
6. At-most-once hold email (`hold_email_at` claim).
7. Notification failure never reverses committed state; no email before commit; no SMTP/slow work under a lock.

## Design rules (4B rules 1–11 carry over: same names/returns/status/messages/check order, `q` executor, join outer tx via `isInTransaction(q) ? run(q) : withTransaction(run, q)`, SQL translations, never load SQLite, CAS guards stay)
1. **Request paths** (`join`, `updateDates`, `confirmHold`, `declineHold`, `leave`): (a) learn the asset: `join` has `assetId`; the others do ONE unlocked `SELECT asset_id FROM waitlist_entries WHERE id = $1` (none → 404 `Waitlist entry not found`, same precedence as SQLite where `processDue` ran first); an invalid/out-of-range asset id → the same refusal SQLite's classify gives (`reserveEligibility(null)` → 404 `Asset not found`), before `lockAsset`. (b) `processDue(pool, assetId)` for THAT asset only, in its own committed transaction (lock → `evaluateAsset` → commit; a refused request still leaves the queue moved). (c) the main transaction: `lockAsset` first, re-read the entry/state under the lock, run SQLite's checks in SQLite's order, write. When joined to an outer transaction the caller must hold nothing dependent (4B rule); in that case the separate `processDue` cannot be its own commit, so a function joined to an outer transaction skips the standalone due step and does the lapse step inside (document). A pool passed from inside a transaction is rejected as nesting (test it).
2. **`processDue(q, assetId?)`:** with `assetId` → that one asset in one transaction. Without → every asset that has an open entry (`SELECT DISTINCT asset_id … WHERE status IN ('waiting','held') ORDER BY asset_id`, an unlocked scan used only to pick assets), **one transaction per asset, ascending id**, never two locks at once. A failing asset is logged (`[waitlist:sweep]`), does not roll back or skip the others; additive return `{ assets, failed: [{ assetId, message }] }` (SQLite returned nothing; this is the one intentional return-shape addition).
3. **`sweep(pool)`** = global `processDue` then `dispatchHoldEmails(pool)`; never throws.
4. **`dispatchHoldEmails(q)`:** global, never inside a transaction, never takes an asset lock. Candidate ids: `status='held' AND hold_email_at IS NULL AND hold_expires_at > NOW ORDER BY id`. Per id, in its own try/catch: claim with one atomic `UPDATE … SET hold_email_at = NOW WHERE id = $1 AND status = 'held' AND hold_email_at IS NULL RETURNING *` (0 rows → skip); then `emit({type:'hold_email', entry})`. A send failure is logged (`[waitlist:mail]`) and the claim stays: **never retried, never duplicated**. **If `!hasNotifier()` it claims nothing and returns 0** (a no-op notifier must not burn claims; SQLite always has a mailer). Returns the number claimed.
5. **`holds_owed` stays a trigger delivered to the notifier (4B contract, unchanged).** `settling` is replaced structurally: every commit that grants a hold (the standalone `processDue` commit, the main transaction's `evaluateAsset`) registers `holds_owed`, so a refused request that moved the queue still triggers the email; the sweep also calls `dispatchHoldEmails` directly so a dropped trigger only delays an email ≤ 60 s. The Slice 5 notifier maps `holds_owed → dispatchHoldEmails(pool)`, `hold_email → PG mailer`.
6. **Lapse-in-the-gap rule (decision D4C-1):** between the standalone `processDue` commit and the main transaction the clock moves (SQLite had no such gap). After `lockAsset` and the re-read, every request path first runs the lapse-recording step (the lapsed-hold / dates-passed / interval-ended closes of `evaluateAsset`, same activity rows), then re-reads the entry, so a hold that expired in the gap is `expired` and gets SQLite's own message (409 "This hold has expired…" etc.). If that transaction then throws, the lapse record rolls back; the hold still counts for nothing (blockers compare `hold_expires_at`) and the next sweep records it.
7. **`confirmHold`:** port the SQLite body exactly, including the `failure` pattern (record, `evaluateAsset`, commit, THEN throw 409 after commit), `ignoreHoldId`, and `insertReservation(… waitlistEntryId, requestGroup)`. It sends no email itself. Return `{ entry, reservation }` with `entry` re-read in the same transaction after the writes.
8. **`updateDates`:** `queue_seq` = per-asset `MAX+1` under the lock; `told` computed from confirmed reservations of other employees; registers `waitlist_joined` with `updated: true` only for newly reached reservers (one per distinct reserver).
9. **`join`:** `classify` under the lock; `insertEntry` (4B) with a new `request_group` (`crypto.randomUUID()`); effects in SQLite's order: `waitlist_joined` per distinct reserver, then `request_recorded { requested: entry, reserved: [], waitlisted: [entry] }`, plus `holds_owed` when its due-step granted a hold.
10. **Effects discipline:** effects registered after the writes they describe; on rollback nothing fires; one flush per transaction; nothing awaited by the caller; `holds_owed` deduplicated per asset per transaction.

## PRODUCT SAFEGUARD
Same as 4B: the serial-order oracle is the acceptance test for every race (operations run through the SQLite modules in every serial order; PG's per-operation outcomes and masked final rows must equal one). SQLite permits: pending ordinary reservations overlapping anything, waiting entries as demand, lapsed holds, an overdue checkout after a reservation, "expected back", 1:00 PM / 1:00 PM adjacency, a hold owner confirming over time recorded meanwhile. A test that conflicts with SQLite is reported with evidence; the module is never "fixed" to satisfy it. Time-dependent cases use fixtures with explicit past/future stamps (no sleeps, no wall-clock boundaries; skip a tier test only within 15 min of UTC midnight with a message). The SQLite writers run with `NC_NO_EXTERNAL_MAIL=1` and a temp `DATA_DIR`; no real mail is ever sent; the PG-side notifier is a recording fake (`installHoldMailNotifier(pool)` helper in test-support maps `holds_owed → dispatchHoldEmails`, `hold_email → recorder`, as Slice 5 will).

## Tests (`test/pg/`, under `npm run test:pg`, skipped by plain `npm test`)
- **Functional/differential twin tests** for all five actions: every refusal branch with identical status+message and check order (403 not-yours, 409 expired, 400 not-offered/closed, "already your dates", held-can't-edit, own overlap/hold/waitlist, ineligible asset/person, start passed, interval ended, confirm-over-blocker → back to waiting + 409, confirm pending-approval asset, admin `removed` vs own `left`); activity rows `action`+`details` identical (incl. "· back of the line", "· removed by IT", "· waiting for IT approval"); `waitlist_joined` `updated` flag; position/phase via the 4A `present` after each action; `queue_seq` ranks.
- **Queue/FIFO/partial/hold:** leave/decline/expiry re-offer to the next eligible entry in FIFO order with correct re-split; partial-day free piece offered, busy piece keeps its place; three tiers and the end-of-interval cap through `processDue`; an older blocked entry does not hold up a younger one.
- **Request-path scoping:** with open entries and a lapsed hold on asset A and asset B, a request on A records only A's expiry (B untouched); the standalone due step commits before the main transaction (refused request still leaves A moved); `sweep` records both.
- **Sweep:** one transaction per asset ascending id (query spy); a failure injected on one asset (trigger) does not roll back or skip the others; `failed` reports it; concurrent `sweep` + `sweep`, sweep vs request, no double offer, no deadlock; sweep never holds two asset locks.
- **Oracle races (2–4 ops, lock held by a third connection until every contender waits, as 4B):** (a) N joins on one asset: distinct per-asset `queue_seq`, order equals a serial order, FIFO afterwards; join vs join of the same person (second refused `own_waitlist`); (b) `confirmHold` vs `confirmHold` (double confirm: one reservation, loser 400 closed); (c) `confirmHold` vs `declineHold`/`leave` by the same person; (d) `confirmHold` vs sweep/expiry with an already-lapsed hold (both orders → 409 expired) and with a live hold (confirm wins, sweep no-op); (e) cancel (4B) vs join on the same asset; (f) leave vs leave, `updateDates` vs `leave`, `updateDates` vs release that grants a hold; (g) sweep vs request on the same asset; (h) different assets independent; pool back to baseline, no waiter left.
- **Gap test:** a deliberately narrow, documented test seam (module-level, not a production argument) fires between the standalone due step and the main transaction to prove rule 6 for confirm, decline and leave.
- **Lock-order guard:** for every new write path the query spy proves the asset `FOR UPDATE` precedes every protected read/write after the single allowed id→asset lookup; the standalone due step locks first too; `ASSET_LOCK_REQUIRED` still fires on unlocked helper calls; nesting via a pool inside a transaction is rejected.
- **Email safety:** (1) at-most-once: N concurrent `dispatchHoldEmails` + a sweep over the same live hold produce exactly one `hold_email`, `hold_email_at` set once; re-evaluation never re-sends; (2) a throwing and a rejecting notifier leave every committed row unchanged, are logged, and the claim is not undone (no retry, no duplicate next sweep); (3) no `hold_email`/`waitlist_joined`/`request_recorded` after a rolled-back transaction, including a failure at the LAST statement of `join`, `confirmHold`, `leave`; (4) a refused confirm that moved the queue still yields exactly one hold email to the next person; (5) no SMTP under lock: a gated slow notifier blocks while a second transaction on the same asset and a `FOR UPDATE NOWAIT` both succeed; (6) no notifier installed → nothing claimed (`hold_email_at` stays NULL), then claimed once after one is installed; (7) outbox parity: the effects of `join`/`updateDates` resolved to recipients equal the SQLite mailer outbox rows for the same scenarios; hold-email recipients/bodies equal SQLite's `waitlistHold` for the same holds.
- **Rollback:** failure injected at the last statement of `join`, `updateDates`, `confirmHold`, `declineHold`, `leave` leaves no row/piece/activity/status change and no effects; FK failure.
- **Mutation checks (each must fail a test; report):** drop the lock in `join`; `lockAsset` after the re-read in `confirmHold`; `queue_seq` MAX over the table instead of per asset; drop the claim `hold_email_at IS NULL` guard; claim without `status='held'`; global instead of asset-scoped request-path due; sweep in one shared transaction; unclaim on send failure; claim when no notifier; register `holds_owed`/`waitlist_joined` before the writes; fire effects on rollback; remove the lapse step of rule 6.
- ×10 consecutive runs of every new/changed suite plus the 4A/4B/pool-transaction suites, 0 skips (report).
